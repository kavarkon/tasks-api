# Общие правила

* Регистрация не выполняет вход. API принимает пароль в поле `password`. Если в форме есть повтор пароля, фронтенд сравнивает значения и не отправляет повтор в API.
* При регистрации и входе API убирает пробелы по краям email и приводит его к нижнему регистру. В ответе email возвращается в этом же виде.
* После входа JWT хранится в cookie `access_token` с `HttpOnly` и `SameSite=Lax` во всех профилях. Только в `prod` добавляется `Secure`.
* Все операции с pack-ами и задачами доступны только авторизованному пользователю и только для его ресурсов.
* `title` pack-а и задачи обязателен, не может состоять только из пробелов и не может быть длиннее 255 символов.
* При обновлении через `PUT` передавайте все поля запроса, не только изменённые.
* Примеры ниже предполагают, что для запросов на изменение передан действительный CSRF-токен.

# Формат ошибки

Общая ошибка сохраняет текущие поля `status`, `message`, `path`:

```json
{
  "status": 404,
  "message": "Pack with id 42 was not found",
  "path": "/api/packs/42"
}
```

Для ошибок валидации дополнительно возвращается `fields`, чтобы фронтенд мог показать ошибки под полями:

```json
{
  "status": 400,
  "message": "Проверьте введённые данные",
  "path": "/api/auth/register",
  "fields": {
    "email": "Некорректный адрес электронной почты",
    "password": "Пароль обязателен"
  }
}
```

# CSRF

## 1 Получение токена

`GET /api/auth/csrf` — доступен без входа.

Ответ: `200 OK`, CSRF cookie и токен для заголовка:

```json
{
  "headerName": "X-CSRF-TOKEN",
  "token": "csrf-token"
}
```

Фронтенд отправляет cookie и указанный заголовок для `POST`, `PUT`, `PATCH`, `DELETE`, в том числе для регистрации, входа и выхода. После входа и выхода фронтенд запрашивает актуальный CSRF-токен заново.

## 2 Отсутствующий или неверный токен

Запрос на изменение без действительного CSRF-токена: `403 Forbidden`. Операция не выполняется.

# Регистрация

## 1 Успешная регистрация

`POST /api/auth/register`

Запрос:

```json
{ "email": "user@example.com", "password": "example-password" }
```

Ответ: `201 Created`.

```json
{ "id": 1, "email": "user@example.com" }
```

## 2 Некорректные поля

Email должен быть корректным адресом длиной не более 255 символов. Пароль не может состоять только из пробелов и должен содержать не менее 8 символов и занимать не более 72 байт в UTF-8. Нарушение этих правил или отсутствие поля даёт `400 Bad Request` с ошибкой в `fields.email` или `fields.password`.

## 3 Email уже зарегистрирован

Регистрация с уже занятым адресом, в том числе отличающимся только регистром: `409 Conflict`. Ответ содержит общее сообщение и ошибку поля `email`. Если одновременно отправить два корректных запроса на регистрацию одного свободного адреса, один получит `201 Created`, другой `409 Conflict`.

# Вход и выход

## 1 Успешный вход

`POST /api/auth/login`

Запрос:

```json
{ "email": "user@example.com", "password": "example-password" }
```

Ответ: `200 OK`, cookie `access_token` и данные пользователя без пароля и токена:

```json
{ "id": 1, "email": "user@example.com" }
```

## 2 Ошибка входа

* Неверная почта или пароль: `401 Unauthorized` и одинаковое сообщение «Неверная почта или пароль». При корректном email непустой, непробельный пароль длиннее 72 байт в UTF-8 даёт тот же ответ, а не ошибку поля, как при регистрации.
* Некорректные или отсутствующие поля: `400 Bad Request`, ошибки возвращаются в `fields`.

## 3 Выход

`POST /api/auth/logout` очищает cookie входа и CSRF и возвращает `204 No Content`. Чтобы повторить выход, сначала получите свежий CSRF через `GET /api/auth/csrf`. С ним повторный выход также вернёт `204`, даже без cookie входа. Скопированный JWT остаётся действительным до истечения его срока.

## 4 Нет авторизации

Чтение защищённого ресурса без действительной cookie `access_token` даёт `401 Unauthorized`. Для запроса на изменение сначала проверяется CSRF: отсутствующий или неверный токен даёт `403 Forbidden`. Если CSRF действителен, но cookie входа отсутствует, JWT повреждён или просрочен, защищённый маршрут вернёт `401 Unauthorized`.

# Страницы списков

* `GET /api/packs` и `GET /api/tasks` возвращают записи по возрастанию ID.
* Без `limit` размер страницы равен 50. Допустимы значения от 1 до 100.
* Для первой страницы не передавайте `afterId`. Для следующей передайте `nextAfterId` из ответа как `afterId`, сохранив фильтр. Вернутся только записи с ID больше указанного.
* На последней странице `nextAfterId` равен `null`. Пустая страница имеет вид `{"items":[],"nextAfterId":null}`.
* Параметры URL `afterId` и `packId` (фильтр списка задач) должны быть положительными 32-битными целыми числами, если они переданы. Некорректный, пустой или состоящий из пробелов параметр `limit`, `afterId` или `packId` даёт `400 Bad Request`.

# Pack-и

## 1 Список своих pack-ов

`GET /api/packs?limit=1` возвращает `200 OK`. Пример первой страницы, если у пользователя два pack-а:

```json
{"items":[{"id":1,"title":"Учёба"}],"nextAfterId":1}
```

Продолжение: `GET /api/packs?limit=1&afterId=1`.

## 2 Свой pack

`GET /api/packs/1` возвращает `200 OK` и сведения о pack-е без задач:

```json
{"id":1,"title":"Учёба"}
```

Для чтения задач этой пачки используйте `GET /api/tasks?packId=1`.

## 3 Создание pack-а

`POST /api/packs`

Запрос:

```json
{ "title": "Учёба" }
```

Ответ: `201 Created`, `Location: /api/packs/1`.

```json
{ "id": 1, "title": "Учёба" }
```

Владелец определяется по авторизации, а не по данным запроса.

## 4 Изменение pack-а

`PUT /api/packs/1`

Запрос:

```json
{ "title": "Учёба и практика" }
```

Ответ: `200 OK`.

```json
{ "id": 1, "title": "Учёба и практика" }
```

## 5 Удаление pack-а

`DELETE /api/packs/1` — `204 No Content`. Задачи этого pack-а также удаляются.

## 6 Ошибки pack-а

* Свой pack не найден либо указанный pack принадлежит другому пользователю: `404 Not Found` при получении, изменении или удалении.
* Пустой, отсутствующий или слишком длинный `title` при создании или изменении: `400 Bad Request` с ошибкой поля.

# Задачи

## 1 Список своих задач

Без `packId` запрос `GET /api/tasks` возвращает задачи из всех своих pack-ов. С `packId` возвращаются только задачи указанного pack-а. Пример ответа `200 OK` на `GET /api/tasks?packId=1`:

```json
{"items":[{"id":10,"title":"Прочитать главу","completed":false,"packId":1}],"nextAfterId":null}
```

Для своего пустого pack-а возвращается пустая страница с `200 OK`. Чужой или отсутствующий pack даёт `404 Not Found`. Пустой фильтр (`?packId=`) даёт `400 Bad Request`, а не список всех задач.

## 2 Получение своей задачи

`GET /api/tasks/10`

Ответ: `200 OK`.

```json
{ "id": 10, "title": "Прочитать главу", "completed": false, "packId": 1 }
```

## 3 Создание задачи

`POST /api/tasks`

Запрос:

```json
{ "title": "Прочитать главу", "completed": false, "packId": 1 }
```

Ответ: `201 Created`, `Location: /api/tasks/10`.

```json
{ "id": 10, "title": "Прочитать главу", "completed": false, "packId": 1 }
```

Указанный `packId` должен принадлежать текущему пользователю.

## 4 Изменение задачи

`PUT /api/tasks/10`

Запрос:

```json
{ "title": "Прочитать главу", "completed": true, "packId": 1 }
```

Ответ: `200 OK` с обновлённой задачей. При изменении `packId` целевой pack также должен принадлежать текущему пользователю.

## 5 Удаление задачи

`DELETE /api/tasks/10` — `204 No Content`.

## Ошибки задачи

* Задача отсутствует или принадлежит другому пользователю: `404 Not Found` при получении, изменении или удалении.
* В JSON для `POST` и `PUT` отсутствующее поле `packId` или значение `null` даёт `400 Bad Request` с `fields.packId`. Если число передано, но pack отсутствует (например, `"packId": -1`) или принадлежит другому пользователю, ответ будет `404 Not Found`. В отличие от тела запроса, фильтр `GET /api/tasks?packId=-1` даёт `400 Bad Request`.
* Пустой, отсутствующий или слишком длинный `title`, отсутствующий `completed` или `completed: null`: `400 Bad Request` с ошибками полей.

## Другие ошибки запроса

* Нечисловой или выходящий за диапазон `id` в пути: `400 Bad Request`.
* Некорректный JSON или тип поля: `400 Bad Request`.
* Если запрос прошёл проверку доступа и CSRF, но маршрут не поддерживает HTTP-метод: `405 Method Not Allowed`. Заголовок `Allow` перечисляет поддерживаемые методы.
* Неподдерживаемый `Content-Type` тела запроса: `415 Unsupported Media Type`. Для создания и изменения pack-ов и задач передавайте `application/json`.
* Неожиданная ошибка сервера: `500 Internal Server Error` без технических деталей в ответе.
